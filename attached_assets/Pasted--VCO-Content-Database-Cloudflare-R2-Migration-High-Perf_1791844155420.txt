# VCO Content Database – Cloudflare R2 Migration & High-Performance Media Delivery

## Objective

Migrate the VCO Content Database from Replit App Storage to Cloudflare R2 as the primary media storage provider.

This is an approved strategic direction. We expect substantial growth in photos, videos, Creator uploads and downloads.

Our priorities, in order:

1. Media security and data integrity
2. Excellent performance and scalability
3. Low and predictable recurring costs
4. Compatibility with all existing features
5. Minimal architectural complexity

Proceed with implementation and development testing. Production cutover, destructive operations and deployment require separate explicit approval.

## 1. Existing System

The recent production audit established:

- 415 production-referenced storage objects
- Approximately 309.49 MB of media
- Approximately 147 MB PostgreSQL database
- Media currently stored in Replit App Storage
- Some legacy Base64 media in PostgreSQL
- Previews currently served through the Replit backend
- Low-resolution downloads generated on demand
- Existing cleanup mechanisms and AI processing workers

Use the existing audit as the technical baseline. Verify any assumptions against the actual code.

Preserve PostgreSQL, media IDs, metadata, galleries, Creator ownership, AI tags, captions, download statistics, Stripe/Credits infrastructure and Nextcloud integration.

## 2. Cloudflare R2 Configuration

Use Cloudflare R2 Standard storage.

Requirements:

- EU jurisdiction restriction
- Private bucket by default
- S3-compatible API
- Least-privilege credentials
- All credentials stored in Replit Secrets
- No public write access
- No public access to original media
- No permanent credentials exposed to browsers

Use the correct EU-specific S3 endpoint.

Prefer a simple bucket structure with logical object prefixes rather than unnecessary separate buckets.

If separate public and private buckets are demonstrably safer or simpler, explain and justify that architecture before implementing it.

Do not enable public bucket access merely to make integration easier.

Provide a list of required Cloudflare settings and Replit Secrets without revealing credential values.

## 3. Storage Architecture

Implement or extend a small provider-independent media storage interface.

Support:

- Upload
- Read
- Stream
- Delete
- Metadata lookup
- Existence checks
- Signed access where appropriate

Cloudflare R2 becomes the target provider.

Retain Replit App Storage as a temporary fallback during migration.

Avoid permanent dual writes and unnecessary storage duplication.

Use stable media identifiers independent of storage provider.

## 4. Media Processing

Preserve existing media rules.

### Official VCO Photography

- Original master files remain in Nextcloud.
- Store one optimised high-resolution derivative in R2, targeting the existing 5 MB maximum.
- Store one lightweight web preview, targeting the existing 100 KB maximum.
- Preserve the best practical resolution and visual quality.
- Do not introduce a fixed 2560px resolution cap.
- Do not create unnecessary additional permanent variants.

### Creator Photography

- Preserve the uploaded original byte-identically.
- Enforce the existing 5 MB upload limit.
- Store one optimised web preview.
- Preserve existing Creator quotas and ownership rules.

### Videos

- Store existing supported video assets in R2.
- Preserve video playback and HTTP Range support.
- Preserve existing video analysis and FFmpeg workflows.
- Do not introduce new video transcoding services without approval.

### AI Processing

- Preserve existing tagging and caption generation.
- Keep temporary processing files bounded.
- Ensure cleanup after successful and failed processing.
- Avoid unnecessary repeated analysis.

## 5. High-Performance Delivery

Performance is a central requirement.

### Public Previews

Design efficient delivery through Cloudflare's edge network.

Requirements:

- Fast global image loading
- Browser and edge caching
- Immutable, versioned URLs where practical
- Efficient cache invalidation
- Minimal Replit bandwidth consumption
- No unnecessary backend processing per image request

Publicly cache only media explicitly approved for public preview.

### Private and Premium Media

Maintain strict access controls.

- No publicly accessible originals
- No bypass of download permissions
- No bypass of premium or Credit restrictions
- No access to unpublished Creator content
- No unauthorised cross-account access
- No caching of protected responses in a publicly accessible form

Evaluate an authenticated Cloudflare Worker or another minimal secure delivery mechanism if required.

Avoid routing large downloads through Replit when a secure alternative is available.

Signed URLs are time-limited bearer credentials, not single-use links. Account for revocation requirements and download statistics.

Do not expose private media through an unrestricted public R2 custom domain.

### Uploads

Evaluate direct-to-R2 browser uploads using short-lived, scoped upload authorisation.

Requirements:

- Preserve server-side upload validation
- Enforce Creator quotas
- Verify completed uploads before publication
- Prevent object-key manipulation
- Prevent unauthorised uploads
- Avoid orphaned objects
- Support reliable upload failure handling

Do not switch to direct uploads if doing so weakens validation or significantly complicates the existing system.

## 6. Download Statistics and Monetization

Preserve existing download tracking.

A successful download authorisation must not be confused with a fully completed file transfer.

Document the current statistics semantics and preserve or explicitly improve them.

Future premium content must remain compatible with:

- Credit purchases
- Paid media unlocks
- Creator earnings
- Stripe payment workflows
- Download entitlements

Do not activate or modify monetization features.

## 7. Migration

Implement a controlled, incremental migration.

### Step A – Prepare

- Configure the R2 storage adapter.
- Validate connectivity.
- Verify bucket jurisdiction.
- Validate credentials and permissions.
- Confirm private access.

### Step B – Pilot

Select a small representative set of existing media.

Include:

- Official photos
- Creator photos
- Previews
- Videos
- Restricted media where available

Copy files to R2 without deleting the originals.

Verify:

- Object size
- SHA-256 checksum
- MIME type
- Metadata
- Ownership
- Read permissions
- Download behaviour
- Video Range requests
- AI processing compatibility

### Step C – Application Integration

Support reading migrated objects from R2.

Preserve existing public gallery URLs and media IDs.

Implement safe provider routing during the transition.

Ensure failures do not silently produce broken media.

### Step D – Performance Validation

Compare existing and R2-based delivery.

Measure:

- Preview loading latency
- Cache hit behaviour
- Replit bandwidth usage
- Download start latency
- Parallel request behaviour
- Video playback
- API response times

Use representative, bounded tests.

Report actual measurements rather than assumptions.

### Step E – Full Migration Preparation

After successful pilot validation:

- Prepare migration of all remaining referenced objects.
- Make migration resumable and idempotent.
- Detect missing or mismatched objects.
- Preserve existing source objects.
- Produce a reconciliation report.

Do not perform the production cutover without approval.

### Step F – Production Cutover

Requires explicit approval.

Before cutover:

- Confirm all objects are verified.
- Confirm rollback readiness.
- Confirm access control tests.
- Confirm performance results.
- Confirm monitoring and error reporting.

Use a controlled cutover with rollback capability.

Do not delete Replit source objects until a separate cleanup approval is given.

## 8. Database and Legacy Media

Keep PostgreSQL as the primary application database.

Do not migrate PostgreSQL.

Preserve existing legacy Base64 media records.

Document a possible future cleanup, but do not perform it automatically.

## 9. Reliability

Implement appropriate safeguards:

- Clear upload and download error handling
- Retry logic for transient storage failures
- Bounded retries
- Idempotent migration jobs
- Object integrity checks
- Orphaned upload cleanup
- Basic storage health monitoring
- Safe fallback during migration

Do not introduce unnecessary infrastructure or additional background services.

## 10. Security Testing

Verify:

- Anonymous access to private media is denied
- Creator A cannot access Creator B's private files
- Unpublished media remains protected
- Premium downloads cannot bypass entitlement checks
- Signed URLs expire correctly
- Revoked permissions behave according to the documented access model
- Upload authorisation cannot be reused outside its scope
- No credentials appear in browser code or logs
- Public caching cannot expose restricted media

Do not enable production delivery until these checks pass.

## Success Criteria

The VCO Content Database can scale to large media collections without depending on Replit for every media transfer.

Public galleries load quickly.

Protected media remains secure.

Existing metadata, Creator ownership, download tracking and future monetization remain intact.

The migration is verifiable, reversible and ready for controlled production activation.
