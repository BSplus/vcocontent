VCO Content Database – AI Tagging, Content Recognition & Usability Improvements

Objective

Improve the existing AI tagging functionality of the VCO Content Database and extend it with motorsport-specific content recognition using Entry Lists and Result Lists.

The goal is to make uploaded media automatically searchable by:

* Race number
* Team
* Listed drivers
* Vehicle and racing class
* Event and series
* Visual content, camera angle, location and atmosphere

Editorial usability takes priority over maximum technical precision.

The user should upload media and let the system do the work. No additional mandatory steps, complex AI workflows or unnecessary confirmation dialogs.

Build on the existing implementation and managed OpenAI connection. Do not rebuild working functionality.

⸻

1. Existing Functionality – Preserve

The current implementation already supports:

* Automatic AI tagging after upload
* Asynchronous background analysis
* Manual tags and captions
* Persistent tagging results
* Retry after failed analysis
* Manual editing and removal of generated tags

Preserve these capabilities.

Do not introduce additional AI providers, separate tagging workflows or new mandatory upload steps.

2. Motorsport-Specific AI Recognition

Extend the existing image analysis to recognize relevant motorsport information.

Identification

Where visually supported, recognize:

* Visible race/car numbers
* Team names or readable branding
* Vehicle manufacturer
* Vehicle model or general type
* Racing class
* Racing discipline

The system must not force precise classifications when visual evidence is insufficient.

For example, a Stock Car must not automatically be classified as a GT Car simply because both are racing vehicles.

Prefer generic but correct metadata over specific but incorrect classifications.

Multiple vehicles

A photo may contain multiple race cars.

Where possible, recognize multiple visible numbers and associate each with its corresponding entry.

Do not assume that the most prominent vehicle represents every car in the image.

Avoid unnecessary object-detection infrastructure. Use the capabilities of the existing vision connection.

3. Entry Lists & Result Lists

Support uploading Entry Lists and Result Lists as event-related reference documents.

Preferred formats:

* CSV
* XLSX
* PDF

Reuse existing upload, document parsing and event management functionality wherever possible.

Supported information

Extract available fields such as:

* Race number
* Team
* Driver(s)
* Vehicle
* Manufacturer
* Racing class
* Event
* Session or race, where applicable

Not every document contains every field. Missing information must not prevent import.

Data association

Entry Lists and Result Lists must be associated with the relevant event.

Where useful, support a season-level Entry List with event-specific updates.

Use the most specific applicable reference information when matching media.

The same race number may belong to different teams at different events.

Never treat a race number as globally unique.

Keep imported reference documents accessible and allow corrections to extracted information.

Avoid duplicate entries when documents are updated or reimported.

Driver identification – pragmatic approach

Driver identification does not need to determine who is physically driving the car.

When a race number can be reliably matched:

* Assign the team.
* Assign the drivers listed for that entry.
* Assign vehicle and class information where available.
* Treat drivers as the official entry lineup, not as visually identified individuals.

If only the team can be reliably identified, assign the team and omit drivers.

If identification is uncertain, leave unsupported fields empty.

Do not introduce facial recognition, helmet-based driver identification or complex driver verification.

Result Lists may supplement or correct Entry List information for the relevant race or session.

Do not infer a driver solely from race position, car appearance or helmet design.

5. Structured Metadata vs. Visual Tags

Keep two logical types of information:

Structured identification metadata:

* Race number
* Team
* Listed drivers
* Vehicle
* Class
* Event
* Series

Descriptive visual tags:

* Camera angle
* Location
* Subject
* Action
* Atmosphere
* Conditions

Both must be searchable.

Do not store all identification information exclusively as unstructured tag strings.

Reuse existing database structures where appropriate.

Do not create an unnecessary parallel metadata system.

6. Usability Improvements

The existing AI tagging flow works, but the interface needs simplification.

A. Automatic workflow

* AI analysis starts automatically after upload.
* The upload dialog can be closed while analysis continues.
* No additional AI action is required.
* Analysis progress and results remain visible when reopening the editor.
* A completed analysis must not be presented as an unfinished task.

B. Clear status messages

Replace technical states such as:

* AI: pending
* AI: completed
* AI: failed

With simple, localized messages:

* Tags werden erstellt …
* Tags hinzugefügt
* Analyse fehlgeschlagen

Show one understandable AI analysis status per image.

Do not expose internal job states or technical provider details to regular users.

C. Upload completion

After successful upload:

* Do not display “Upload 0 Files”.
* Show a clear completion state.
* Allow the user to close the dialog immediately.
* Continue AI analysis in the background.

Do not require users to wait for AI tagging before continuing their work.

D. Simplified tag editing

Show all currently saved tags in one editable list.

* AI-generated tags and manual tags can be edited or removed.
* Do not prominently display historical AI suggestions as a separate set of chips.
* Do not require users to accept every AI tag individually.
* Manual changes must persist.
* AI analysis must not restore tags that the user intentionally removed from the same analysis result.

A technically useful distinction between AI and manual origin may be retained internally, but it should not complicate the normal editing interface.

E. Remove redundant AI actions

After successful analysis, do not continue displaying “Auto-Generate Tags” as though analysis has not happened.

If a reanalysis action is provided, it must actually start a new analysis rather than silently return the cached result.

Make reanalysis a secondary action, not a prominent primary button.

Never overwrite manually confirmed metadata during reanalysis.

F. Fresh analysis status

When reopening a media editor, retrieve the current analysis state.

Do not rely solely on the existing global five-minute freshness setting.

A completed or failed background job must become visible without requiring a full page reload.

Avoid unnecessary continuous polling.

G. Identification display

Show recognized identification information in the existing media editor.

For example:

Race Number: 32
Team: Example Racing
Drivers: Driver A, Driver B
Class: GT3

The listed drivers are associated with the entry, not individually identified in the photograph.

Allow users to correct these fields easily.

If a match is uncertain, do not present it as a confirmed identification.

Do not create a complex confidence-score interface.

H. Captions

Keep caption generation separate from AI tagging.

Preserve manually written captions.

Do not overwrite editorial text automatically.

I. Language consistency

Respect the existing application language.

Do not mix German helper text with English controls in the same interface.

Translate user-facing statuses and actions consistently.

Do not translate stored team names, driver names, event names or official racing classifications.

J. Responsive usability

Maintain the existing responsive editor behavior.

Ensure that:

* Tags remain readable and editable.
* Identification fields are accessible.
* Save buttons remain reachable.
* No horizontal overflow occurs.
* Dialogs remain usable on narrow mobile viewports.

Do not redesign the entire application.

7. Search Compatibility

Ensure that the new information can be used by the existing search and filtering functionality.

Examples of desired searches:

* Team name
* Race number within an event
* Listed driver name
* GT3 + Front View
* Cockpit + Helmet
* Night + Race Action
* Pit Lane + Atmosphere

Use existing search infrastructure wherever possible.

Do not implement a new semantic search engine, conversational search interface or dedicated AI search dashboard as part of this task.

8. Reliability & Editorial Control

* AI analysis must not block uploads.
* Provider failures must not cause data loss.
* Manual metadata always takes precedence.
* Unknown information should remain unknown.
* Do not invent drivers, teams or vehicle identities.
* Preserve previous successful analysis results if a later reanalysis fails.
* Keep the existing retry mechanism.
* Avoid unnecessary repeated provider calls.
* Keep uploaded Entry Lists and Result Lists subject to existing access permissions.

9. Focused Validation

Perform proportionate tests using a small representative set of authorized VCO media.

Include:

1. A vehicle with a clearly readable race number and matching Entry List.
2. A vehicle without a matching entry.
3. Multiple race cars in one image.
4. A partially obscured race number.
5. A cockpit or helmet detail.
6. An atmosphere or paddock photograph.
7. The previously misclassified stock-car-89 example.

Verify:

* Correct mapping to event-specific entries.
* No invented driver identification.
* Correct handling of unknown or ambiguous information.
* Preservation of manual tags and captions.
* Background processing and retry behavior.
* Fresh status when reopening the editor.
* Simple desktop and mobile editing.

Distinguish technical test success from actual recognition accuracy.

Do not run an extensive benchmark or production-wide reanalysis.

10. Implementation Approach

Before coding:

Briefly inspect the existing implementation and identify reusable components for:

* AI analysis
* Tag taxonomy
* Media metadata
* Event management
* Document uploads
* Search and filtering
* Localization

Then implement the smallest reasonable extension.

Do not introduce:

* New AI providers
* Facial recognition
* Separate review dashboards
* Mandatory approval workflows
* Complex confidence interfaces
* Large architectural rewrites
* Additional upload steps

If a requested feature would require substantial new infrastructure, report this before implementing it rather than expanding the scope automatically.

11. Final Report

After implementation, provide a concise report covering:

1. Existing components reused
2. Functional changes
3. Taxonomy additions
4. Entry List / Result List integration
5. Usability improvements
6. Actual test results and recognition limitations
7. Remaining issues

Primary success criterion:

A VCO editor uploads a photo, the system automatically generates useful visual tags and identifies matching entries where reference data is available, and the editor can immediately search, review or correct the result without unnecessary interaction.
